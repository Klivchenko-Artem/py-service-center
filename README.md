# Сервисный центр: Django с рабочей админкой

Учёт заявок на ремонт техники: приём заявки без регистрации, работа мастеров
в админке, права по ролям, статусы, сроки и просрочка. Django 6 + PostgreSQL,
21 тест на pytest, поднимается одной командой.

Админка здесь не «зарегистрировал модель и ладно», а рабочее место: цветные
статусы, фильтр просроченных, массовые действия, сводка над списком и
ограничение видимости по правам.

## Как устроено

```
config/            настройки, корневые маршруты, wsgi
service/models.py  клиенты, устройства, заявки, комментарии + менеджер заявок
service/admin.py   админка: колонки, фильтры, действия, права
service/forms.py   формы публичной части, нормализация телефона
service/views.py   витрина, приём заявки, проверка статуса
service/management  команда seed_demo: группы прав, сотрудники, демо-заявки
templates/         шаблоны публичной части и вставка сводки в админку
tests/             21 тест: модели, публичная часть, админка и права
```

Что стоит посмотреть:

- Права живут в менеджере модели (`TicketQuerySet.for_user`): мастер видит
  свои заявки и ничьи, приёмщик с правом `view_all_tickets`, все. Одно правило
  работает и в админке, и в тестах, а не переписывается в каждом шаблоне.
- Номер заявки формата `26-0013` (`Ticket._next_number`): год плюс счётчик
  внутри года: клиенту его диктуют по телефону, и «487» звучит хуже.
- Дата закрытия ставится сама и снимается, если заявку вернули в работу.
  Руками её забыли бы, а по ней считается срок ремонта.
- Своя форма поверх трёх моделей (`TicketRequestForm`): посетителю незачем
  знать про клиента, устройство и заявку по отдельности; телефон нормализуется,
  постоянный клиент находится по нему, а не заводится второй раз.
- Счётчики в списке клиентов считает база (`annotate`), а не питон в цикле:
  иначе список из ста клиентов делает двести лишних запросов.

## Запуск

```bash
docker compose up -d
docker compose run --rm --user root --entrypoint sh web -c "python manage.py seed_demo"
```

Миграции и статика накатываются в `entrypoint.sh`, суперпользователь заводится
из переменных окружения. Порты подвигаются: `HTTP_PORT=8003 POSTGRES_PORT=5436`.

| Что | Где |
| --- | --- |
| Витрина | http://localhost:8002/ |
| Оставить заявку | http://localhost:8002/new/ |
| Узнать статус | http://localhost:8002/status/ |
| Админка | http://localhost:8002/admin/ |

Учётные записи стенда (пароль у всех `stand-password`): `admin` (суперпользователь),
`manager` (приёмщик, видит все заявки, умеет закрывать), `master`
(мастер, видит свои и ничьи, закрывать не может). Пароли стендовые и напечатаны здесь же,
в репозитории нет ни одного настоящего секрета.

## Что показывает админка

- Список заявок: номер, клиент, устройство, цветной статус, приоритет,
  мастер, срок (просроченный подсвечен красным), стоимость.
- Фильтры: статус, приоритет, мастер и свой фильтр «просрочены», которого
  нет среди полей модели.
- Массовые действия: «взять в работу» (проставляет исполнителя), «отметить
  готовыми» (только с правом `close_ticket`), «поднять приоритет».
- Комментарии инлайном, автор подставляется из текущего пользователя.
- Сводка над списком: сколько в работе, сколько просрочено, средний чек.
- Мастер видит только своё: заявки коллег не появляются даже по прямой
  ссылке.

## Решения, которые стоит объяснить

- Статус проверяется по номеру и телефону. Номера идут подряд, и по одному
  номеру можно было бы листать чужие заявки.
- Приём заявки через POST с редиректом. Обновление страницы после отправки не
  должно заводить второй такой же ремонт.
- `on_delete=PROTECT` у клиента и устройства в заявке. Удаление клиента не
  должно молча уносить историю ремонтов; сначала разберитесь с заявками.
- Уникальность серийника через частичный индекс. Пустой серийник (стёрся, нет
  наклейки) это обычное дело, а два одинаковых непустых означают, что аппарат
  завели дважды.
- Настройки https включаются переменными. Жёстко включённый
  `SECURE_SSL_REDIRECT` сделал бы локальный стенд недоступным; на проде переменные
  ставятся в `True`.
- gunicorn, а не `runserver`. Сервер разработки в контейнер не кладут даже
  для демонстрации.
- Статику отдаёт whitenoise. Отдельный nginx ради двух css-файлов это лишний
  контейнер на стенде.

## Тесты

```bash
make test    # pytest в контейнере
make lint    # ruff
```

21 тест: генерация номеров подряд, автоматическая дата закрытия и её снятие при
возврате в работу, просрочка только у открытых заявок, видимость по правам
(мастер, приёмщик, свободные заявки), нормализация телефона и повторная заявка
без дубля клиента, редирект после отправки, чужая заявка по номеру не
показывается, а в админке проверены массовые действия, отказ закрывать без права,
подстановка автора комментария, сводка и фильтр просроченных.

CI гоняет ruff, `manage.py check --deploy`, проверку «миграции не отстали от
моделей» (`makemigrations --check`) и тесты на живом PostgreSQL.

## Чего здесь намеренно нет

- DRF и API. Это проект про Django и его админку; REST уже показан
  в соседнем проекте на FastAPI.
- Кастомной модели пользователя. Менять `AUTH_USER_MODEL` ради ролей не
  нужно: роли живут в группах и правах, для чего они и сделаны.
- Уведомлений клиенту. Почта и СМС это внешние сервисы и ключи к ним,
  а не то, что стоит изображать заглушкой.
